# Issue #181：并发上传与断点续传设计

状态：Phase 1 已实现（本地）；Phase 2 断点续传会话未实现。关联：https://github.com/SwartzMss/Rain/issues/181

## 1. 目标与现状

目标是让多个文件独立上传、失败可恢复，并明确区分网络传输与后台处理。不能预设“一个 HTTP 请求必然无法跑满带宽”，性能收益需要测量。

当前代码事实：

- `frontend/src/features/files/hooks/useUploadTask.ts` 只有一组上传状态；多选文件一次交给 `uploadLogs`。
- `frontend/src/api/client.ts` 把全部文件放在一个 multipart 请求中，通过 XHR 显示整批传输进度。当前不是多个独立请求的串行队列。
- `backend/src/routes/uploads.rs` 每个请求创建一个 Bundle，接收完成后启动后台任务并返回 202。多选文件目前属于同一个 Bundle。
- `backend/src/upload/job.rs` 已分离接收、处理并发；先完成整包解压预检和配额检查，再处理文件、建立索引和发布。
- `backend/src/upload/multipart.rs` 的临时空间账本在内存中，生命周期依赖 reservation 对象。
- `backend/src/main.rs` 启动时清理 `.tmp`；数据库恢复逻辑会将遗留 PENDING/PROCESSING Bundle 判为失败。续传会话不能直接沿用这套生命周期。

本次设计保持现有压缩包限制、Tantivy 索引架构和本地存储。分片改变传输方式，不增加允许上传的内容总量。

## 2. 方案比较与推荐

| 方案 | 收益 | 代价/边界 |
| --- | --- | --- |
| 仅前端并发队列 | 最快改善多文件进度和吞吐 | 单个大文件中断仍要重传 |
| 并发文件队列 + 单文件顺序分片（推荐） | 支持暂停、恢复、分片重试；无需合并副本 | 不提供单文件多连接加速 |
| 并发文件队列 + 单文件乱序并发分片 | 在特定网络中可能改善单文件吞吐 | 分片清单、乱序写入/合并、磁盘峰值与恢复逻辑更复杂 |

先实现队列，再实现顺序分片。首版每文件只允许一个在途分片；用不同文件之间的并发利用带宽。仅当测量证明单文件吞吐受请求串行限制时，再设计乱序分片，不能直接增大连接数作为默认优化。

## 3. 上传单位和交互

推荐新前端采用“一个用户选择的顶层文件 = 一个任务 = 一个 Bundle”。选择三个 ZIP 会出现三个任务；一个 ZIP 内部的嵌套 ZIP 仍归同一个 Bundle，内部文件不拆上传任务。

这是明确的产品语义变化：过去多选文件属于一个 Bundle，以后独立成功、失败和删除。不自动按文件大小打组。旧 multipart API 继续兼容原来的多文件 Bundle，已有数据不迁移。

上传队列放在登录后的应用层，独立于 Issue 页面。任务创建时固定用户、Issue、文件和任务 ID，切换 Issue 只过滤展示，不改变正在上传任务的归属。注销时中止传输、清除内存文件引用；服务端会话按期限保留，其他用户不能恢复。

展示每个文件的名称、大小、传输进度、状态、错误与可执行操作；页面保留“上传中 N、等待 N、处理中 N”的摘要。后台处理中允许继续加入文件。

- 传输状态：等待、上传中、等待重试、已暂停、等待重新选择文件、上传已确认、已取消、已过期。
- 处理状态：等待处理、校验、解压、索引、发布、可用、处理失败。
- 网络发送到 100% 后显示“等待服务器确认”；只有接收/完成接口确认后才显示“上传完成，等待处理”。只有 Bundle READY 才显示“可用”。
- 解压与索引没有可靠总量时只显示阶段和已知计数，不伪造百分比。现有 VALIDATING/EXTRACTING 会反复切换，不要求阶段严格单调。
- Phase 1 的 multipart 只有整文件重试与中止，没有真正暂停续传。Phase 2 启用分片后再展示暂停/继续。

## 4. Phase 1：前端队列

默认同时上传 2 个文件，单个任务调用现有 multipart API 并只携带一个文件。调度器必须覆盖整个应用，不在每个 Issue 页面分别建立并发池。首版“全局”指一个浏览器标签页；跨标签页/用户总量由后端 receive permits 兜底。

每个任务持有独立 XHR、中止控制、进度和错误。只要收到接收确认就释放传输槽位，后台索引不占上传槽位。轮询按 Issue 合并请求，页面卸载不终止应用层队列，旧响应不能写入其他 Issue。

429 接收繁忙采用带抖动的退避，有 Retry-After 时遵循服务端值。旧 multipart 遇到网络断开、5xx 或响应丢失时，可能已被服务器接收：首版显示“接收结果未确认”，刷新 Bundle 列表并要求用户核对，不能自动无限重发，也不能仅按同名文件认定是同一上传。这个问题由 Phase 2 的幂等会话解决。

传输中的取消中止请求；如果服务端已接收，任务转入后台处理状态，不能假装已取消。后台处理取消不纳入本 Issue 首版。

## 5. Phase 2：持久化会话与顺序分片

建议文件达到 64 MiB 时默认分片，小文件沿用 multipart；64 MiB 是初始调优值。服务端返回固定分片大小，初始为 8 MiB，最后一片可不足；同一会话分片大小不变。全局默认 2 个在途文件传输请求，每文件最多 1 个；顺序追加避免合并时额外复制整份压缩包。

一个会话在完成传输前不创建 Bundle；归属和接收记录存放独立表。未过期的会话必须纳入 Issue 自动清理保护条件，手动删除 Issue 则使其失效并回收文件。会话只描述传输，Bundle 仍描述处理结果。

### API 契约（建议）

| 接口 | 行为 |
| --- | --- |
| `POST /api/issues/{code}/upload-sessions` | 创建会话；提交文件名、大小、lastModified、幂等键；返回 session ID、分片大小、offset、过期时间 |
| `GET /api/issues/{code}/upload-sessions` | 列出当前用户在该 Issue 的可恢复会话；分页 |
| `GET /api/upload-sessions/{id}` | 返回权威已确认 offset、传输状态、期限及完成后的 task_id |
| `PUT /api/upload-sessions/{id}/chunks/{index}` | 原始二进制请求，携带预期 offset 和 SHA-256；校验长度、序号及摘要后确认 |
| `POST /api/upload-sessions/{id}/complete` | 冻结输入，验证完整文件摘要及长度，幂等创建一个 Bundle 和持久处理入队记录 |
| `DELETE /api/upload-sessions/{id}` | 取消未交付会话；重复取消幂等；已交付返回状态冲突和对应 task_id |

所有接口校验登录用户、Issue 所有权和活动状态，写接口沿用 same-origin 防护；session ID 不是访问凭据。用户提供的文件名仅作展示，磁盘路径由服务器 ID 生成。

创建幂等键唯一范围为用户、Issue、键。同一个键参数不同返回 409。complete 响应丢失后查询或重试必须返回原 Bundle，不得新建第二份。

### 分片一致性

服务端只接受 `offset == committed_offset` 的下一片，序号、大小由服务端根据会话计算。分片直接追加到独占输入文件，流式计算摘要，禁止在内存收集整份文件。失败或摘要不符时截断到原 offset。

每个分片先完成写入和文件同步，再用短数据库事务记录分片摘要、长度和新 offset；文件 I/O 不能持有 SQLite 写事务。写入后、数据库提交前崩溃时，恢复截断超出已确认 offset 的尾部。若实际长度小于已确认值，标记损坏并要求重新上传，不能声明可续传。

相同序号/长度/摘要的已确认分片重复发送只返回原确认，不重新计费或追加；内容冲突返回 409。超前分片返回权威 offset，客户端同步状态后继续。会话级排他锁覆盖追加、完成、取消与回收，取消须等待在途写操作结束。首版部署模型为单后端进程、本地数据目录，不支持多个进程同时接收同一会话。

完成请求转入 FINALIZING，拒绝新分片；完整文件 SHA-256 校验在受限后台任务中执行，API 可返回 202，并通过查询接口报告进展。数据库事务同时创建 Bundle、唯一 session→bundle 关联和处理队列记录，随后才返回交付成功。FINALIZING 可重启恢复；重复 complete 不重复校验调度/创建 Bundle。

处理器通过持久队列领取任务，记录领取状态，避免“数据库已提交、spawn 尚未执行”导致永远没有处理。未领取任务可重启入队；已经开始解压/索引的任务在重启后沿用失败语义，不承诺后台索引断点恢复。必须修改旧启动恢复的筛选条件，避免误伤尚未领取的新队列任务。

### 浏览器恢复

页面未关闭时，暂停中止在途请求；恢复先查询 offset，最多重传未确认的一片。

IndexedDB 仅保存会话标识、归属、文件元数据和已确认分片摘要，不保存整个文件。刷新/关闭浏览器后需要用户重新选择本地文件，不能承诺浏览器自动重新取得文件访问权限。

文件名、大小、lastModified 只能筛选候选。续传前用 Web Worker 分片读取所选文件，验证已确认前缀的所有分片摘要；不匹配就拒绝续传。完整文件摘要也采用增量计算，可与这次扫描/后续分片读取衔接；禁止把大文件一次性读入内存。摘要计算库与浏览器兼容性是实现前的技术验证项。

进度区分“本次已发送”和“服务端已确认”，重试不累计重复字节。完整性校验单独显示状态，不能算作文件已可用。

## 6. 空间预算与权限生命周期

始终分开计算上传压缩字节、解压工作字节、Issue 最终非压缩内容字节。ZIP 大小不能预测最终日志大小；接收完成不代表通过 8 GiB 配额检查。沿用完整预检后再索引的顺序，预检按 Issue 原子预留最终内容，失败释放。

续传输入使用 `.uploads/{session_id}`，与启动清空的 `.tmp` 分离。会话保留期限建议为成功写入最后一个新分片后的 24 小时，创建起最长 7 天；只查询状态或重发旧片不能延长期限。每用户建议最多 4 个未交付会话，并对创建操作限流；只在调度到任务时创建服务端会话。

新会话按声明文件长度原子预留接收空间，服务端严格执行实际长度限制。预留和旧 multipart、解压空间共同受现有全局临时空间上限控制：需要统一预算协调入口，不能分别拥有两个都以为“还有 32 GiB”的账本。声明长度过大仍按现有单次上传上限拒绝。

启动先对账数据库与磁盘、重建预算，再开放接收。预留是容量承诺；遗留部分文件、解压输出和清理失败文件仍计费。管理员降低上限时允许账面暂时超额，但禁止新增占用，保留已存在数据等待完成或清理。

交付后通过同盘原子移动/所有权转移把输入交给现有后台处理流程，预算随之转移，不能重复扣费或提前释放。跨目录移动的崩溃窗口由持久 handoff 记录恢复；若处理流程需要复制，复制前必须计入额外空间。

取消、过期、Issue 删除先禁止新写入，再移入清理状态；真正删除成功后才释放预算。Windows 文件锁导致清理失败时进入现有重试思路，仍保持占用。所有清理操作只作用于服务端生成并验证的会话路径。

## 7. 错误处理

- 网络失败/超时：查询 offset 后指数退避重试失败分片，默认最多 5 次，耗尽后保留会话并显示“等待手动继续”。
- 接收繁忙/临时预算不足：释放调度槽位，等待后重试；不能导致所有文件同时密集重试。
- 401：暂停队列，重新登录后同一用户才能恢复；403/Issue 删除：终止相关任务。
- 409 offset 冲突：同步服务器状态；摘要/文件冲突需要重新选择或重新创建任务。
- 410 会话过期：明确说明需重新上传。
- Issue 内容超限/压缩包安全校验失败：显示后台处理错误，不自动重新传输相同文件。
- 分片上传成功但处理失败：仍可查看对应 Bundle 的失败原因；首版不承诺自动重用输入重新索引。

配额提示应说明“已占用包含本次处理中已计入的内容；接下来这个文件需要 X，剩余 Y”。当前报错的 10 MiB 是触发失败那次 reserve 的文件大小，可能是大 ZIP 内的一份日志，不一定是整个上传大小。

## 8. Phase 3：基于测量优化后台等待

现有流程已支持上传完成后后台处理；新队列使先上传完的文件能在其他文件仍传输时进入处理。

先分别测量接收时间、处理排队、预检/解压、索引、发布耗时和磁盘峰值。首版不做“边接收 ZIP 边解压索引”，也不打破整包安全预检后才索引的顺序。若后续要改变预检边界，应另行设计资源释放、失败回滚和索引可见性。

## 9. 验收与测试

Phase 1：

- 多文件单独显示进度与结果，同时传输不超过 2；失败不阻止其他文件，202 后槽位及时释放。
- 切换 Issue、离开文件页面、重新选择文件不会把任务挂到错误 Issue；重复文件名使用独立任务 ID。
- 429 退避、结果未确认、取消与服务器接收竞态、后台失败展示有前端行为测试。
- 明确验证新前端一文件一 Bundle、旧 API 多文件一 Bundle 的兼容性。

Phase 2：

- 在任意分片断网、丢响应、暂停、刷新、服务器重启，确认前缀保留；恢复最多重传未确认片，文件摘要正确。
- 测试最后一片、空文件、错误长度、错误摘要、乱序/重复请求、并发 complete、取消与写入竞态。空文件允许创建并直接 complete，后续文件处理沿用既有规则。
- 对“文件写完/数据库提交前”“完成校验后/入队前”“入队后/worker 领取前”“移动输入前后”注入崩溃，验证一致性与无重复 Bundle。
- 刷新后选择同名同大小但内容不同的文件必须拒绝混合续传。
- 测试跨用户访问、Issue 删除、会话过期、磁盘满、预算降低、清理失败和重启预算重建。
- 嵌套 ZIP 中间容器不占 Issue 内容配额，最终日志只计算一次；archive bomb 各项限制与当前行为一致。
- Linux 和 Windows 都执行文件写入、截断、移动、取消及清理测试。

性能验证使用代表性单文件、多文件、受限带宽和丢包场景，对比吞吐、失败重传字节、上传至 READY 延迟、内存和临时磁盘峰值。不以“并发一定更快”作为验收；断网后不从头传大文件、资源使用有界是硬性要求。

## 10. 交付边界

拆成两份独立实现任务：Phase 1 队列与状态展示；Phase 2 会话协议、持久化与恢复。Phase 3 保留为测量后的独立优化。初始阈值和并发是建议默认值，服务端返回有效能力，前端不猜测容量。

Phase 1 已实现：前端应用级受控并发队列、每文件独立 multipart 请求、独立进度/接收状态、429 退避、失败手动重试和 Issue 过滤展示；后端协议与归档/配额处理未改变。Phase 2 持久化会话、顺序分片和浏览器恢复仍未实现。本次未创建 Release。
